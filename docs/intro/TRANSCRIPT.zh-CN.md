# 解说全文

## 手上有文献，下一步呢？

你有一份文献清单，也下载了一些论文。接下来，怎样把它们变成一轮真正能核对的审阅？

这两个 skill 分别帮你准备全文和组织审阅。你可以连着用，也可以从自己需要的那一步开始。

## 先把手头材料交给它

先给它研究问题、文献清单和已有 PDF。有 protocol 或编码规则，也一起带上，初稿就可以。

比如你可以说：帮我找清单里缺的全文，保留文献 ID。需要我操作时，告诉我具体做哪一步。

## 找不到，就有依据地换路径

它会先核对已有资料，补上缺的标识，再尝试公开来源、出版社或仓储。失败的路径也会记下来。

如果你有学校图书馆权限，它还会查相关资源和访问入口。直接付费的页面，有时还有另一条可用路径。

## 需要人时，把这一小步说清楚

有时只差你登录、完成验证，或者把能打开的文件保存下来。它会交代文章、入口、操作和交回位置。

你把文件交回来，它继续核对；其他能获取的文章可以先处理。人交回的文件，也一样要检查。

## 拿到文件，还要确认拿对了

PDF 能打开，不代表一定找对了。还要核对文章或章节、DOI、版本和完整性，并记录页数与文件标识。

如果文本解析有问题，就换方法检查；身份仍不清楚，就留下待核对项。不会把一个文件名当成证据。

这一段结束，你拿到的是核对过的来源、尝试记录和剩余清单。已有合适全文的人，可以直接接到下一步。

## 规则由人发展，轮次由你决定

进入审阅前，研究团队先发展编码规则。可以先选一小批样本，比如十篇，讨论哪些定义还需要调整。

规则够清楚后，再让 AI 整理下一批，交给人核验。也可以回到校准，或换成独立审阅。

## 审阅方式可以选

AI 辅助模式会展示编码建议和出处。独立模式则给人规则、原文和空白表单，不放 AI 建议与他人反馈。

这是通用示例里的独立表单。人可以先自己判断，再把答案交回来；这一轮用什么模式，由团队决定。

## 把一条判断带回原文

来看实际的 Pilot 工作台。中间是待核对的条目，右边是原文。点页码，就能回到对应页面。

找到匹配的引文时，阅读器会标黄。接着要读上下文，判断这句话是否真的支持编码。

核对后可以确认，也可以点 Revise，写出哪里需要改。画面里的演示反馈单独保存，不是正式研究判断。

## 每个人可以有自己的任务

你可以按人分配文献、字段、说明和审阅模式。比如一位核对方法，另一位关注概念。配置由 agent 准备。

审阅者打开自己的包，就能在浏览器里工作。看完后导出 JSON 发还，不需要安装 AI，也不需要共享一个账号。

## 回传之后，人来解决分歧

Agent 核对回传属于哪一轮、覆盖了哪些条目，再整理不同意见。研究团队对照证据，决定最后怎样处理。

如果 PDF 或规则后来变了，保留旧版本，找出受影响的工作，再开启需要重做的一轮。

## 两个案例，看到什么能复用

TALL 用在原始实证研究，Agency 用在综述层面的研究。研究单位和规则不同，但来源、反馈、裁决的连接方式可以复用。

复用时，换成你自己的研究问题、codebook 和任务配置。这两个案例进度不同，也不能当成已经证明效率的对照实验。

## 选一个入口，开始你的第一轮

两个 GitHub 页面都有安装说明和例子。协调者把对应文件夹装到支持 skill 的 agent 里；想先看界面，也能打开模拟审阅包。

有全文和初稿规则以后，可以这样问：按我们选定的样本准备审阅包，说明缺口，以及哪些判断还需要我们来做。

这套流程想省下的是找资料、搬信息和反复对照的工作。规则怎样发展、证据怎样理解、结论怎样形成，仍然由人掌握。
